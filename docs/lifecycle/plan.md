# Blaster Plan Lifecycle Specification

The planning phase is responsible for transforming the synchronized endpoint configuration generated by blaster parse into a deterministic execution plan that the runtime can execute without performing additional reasoning.

Unlike traditional API testing tools that execute requests directly from an OpenAPI document or from manually written collections, Blaster first analyzes the complete endpoint configuration, discovers execution dependencies, determines resource requirements, organizes execution stages, and produces an immutable execution plan before any HTTP request is sent.

The planner never performs authentication, sends network requests, generates payloads, validates responses, or modifies backend resources. Its only responsibility is deciding what should execute, when it should execute, and what runtime information will be required during execution.

The generated execution plan becomes the single source of truth for blaster run. Runtime workers never change execution order or make planning decisions during execution.

## Phase 1 — Load Planning Metadata

Blaster begins by loading the synchronized endpoint configuration together with the current project configuration, OpenAPI specification, planner hints, dependency definitions, authentication metadata, semantic definitions, and every runtime configuration produced during the parsing phase.

At this stage the planner only constructs an internal representation of the project. No dependency analysis or execution ordering is performed yet. Every endpoint, request schema, response schema, semantic configuration, planner hint, validator configuration, authentication requirement, payload strategy, and execution option is collected into memory so subsequent planning phases operate on a complete and deterministic project model.

## Phase 2 — Dependency Analysis

After every endpoint has been loaded, Blaster analyzes relationships between endpoints in order to determine which operations depend on the successful execution of others.

Dependency analysis combines multiple deterministic information sources including explicit dependency declarations defined by developers, semantic relationships generated during parsing, resource identifiers, endpoint structures, REST naming conventions, authentication requirements, reusable resources, and planner-specific configuration.

Whenever a dependency can be determined deterministically, it becomes part of the execution graph. Whenever insufficient information exists to confidently infer a dependency, Blaster intentionally treats the endpoint as independent rather than making uncertain assumptions. The planner always prioritizes deterministic execution over aggressive optimization.

The planner never attempts to understand business workflows beyond the information explicitly available inside the endpoint configuration. Unknown relationships remain independent unless developers provide additional planner hints.

## Phase 3 — Execution Stage Construction

Once dependency analysis completes, Blaster transforms the dependency graph into an ordered sequence of execution stages.

Each execution stage contains endpoint operations that can safely execute concurrently without violating dependency constraints or introducing predictable execution conflicts.

Endpoints that require the successful completion of previous resources are automatically scheduled into later execution stages, while independent endpoints are grouped together whenever possible to maximize concurrency without sacrificing deterministic behavior.

The planner guarantees that every execution stage has a well-defined boundary. Runtime always completes one stage before continuing to the next stage, ensuring that state validation remains isolated from unrelated resource modifications occurring later in the execution plan.

## Phase 4 — Resource Planning

After execution stages have been established, Blaster determines which runtime resources will be required before each stage begins.

Instead of creating resources itself, the planner simply records resource requirements that runtime must satisfy during execution.

These requirements may include authentication, reusable identifiers, existing resources, seed data, state snapshots, planner variables, dependency references, or any additional execution prerequisites required by subsequent stages.

The planner never decides how resources are created. It only specifies which resources are required and when they must be available so runtime can prepare them immediately before execution begins.

## Phase 5 — Validation Planning

The planner determines the validation strategy required for every endpoint operation.

Read-only operations may require only transport-level validation, while state-changing operations such as POST, PUT, PATCH, and DELETE automatically require additional backend state validation after execution.

Planner hints, semantic definitions, endpoint metadata, and validation configuration generated during parsing are combined to determine which validation layers will execute during runtime.

The planner also determines whether optional AI interpretation may be invoked when deterministic validation cannot confidently classify a result. AI participation is recorded only as an execution capability and never modifies the deterministic execution plan itself.

## Phase 6 — Execution Task Generation

After every planning decision has been completed, Blaster converts every endpoint operation into immutable execution tasks.

Each task contains every piece of information required by the runtime, including execution stage, HTTP method, endpoint reference, payload strategy, semantic configuration, authentication requirement, validation strategy, planner variables, dependency references, resource requirements, execution priority, and every additional runtime option required during execution.

Runtime workers never perform planning or dependency analysis. They simply receive immutable execution tasks generated by the planner and execute them exactly as defined.

## Phase 7 — Freeze Execution Plan

When task generation finishes, Blaster locks the entire execution plan.

From this point forward no additional dependency analysis, execution ordering, semantic reasoning, or planner decisions are permitted.

The execution plan becomes immutable and serves as the single execution source for blaster run.

Every runtime component including authentication, resource preparation, concurrent workers, validation, runtime state tracking, reporting, and optional AI interpretation operates exclusively on this execution plan without modifying its structure.

This separation guarantees that repeated executions always produce identical execution order whenever the endpoint configuration remains unchanged, providing deterministic behavior suitable for local development, automated regression testing, and continuous integration pipelines.

Planner Design Philosophy

The planner is the decision-making component of Blaster but never participates in execution.

Its responsibility is not to understand business logic, execute requests, generate payloads, validate responses, or communicate with external systems. Instead, its sole objective is transforming deterministic endpoint metadata into the safest and most reproducible execution schedule possible.

Whenever complete information is unavailable, the planner intentionally prefers deterministic behavior over speculative optimization. Rather than guessing hidden business relationships, Blaster preserves predictable execution by treating uncertain endpoints as independent until developers explicitly provide additional planning metadata.

By separating planning completely from runtime execution, Blaster ensures that every execution decision is made only once before any HTTP request is sent, allowing runtime to remain lightweight, highly concurrent, reproducible, and suitable for automated CI/CD environments.
