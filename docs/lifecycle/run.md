Blaster Run Lifecycle Specification

The runtime phase is responsible for executing the endpoint configuration previously generated by blaster parse.

Unlike traditional API testing tools that simply replay requests or execute manually written test cases, Blaster follows a deterministic execution plan that coordinates authentication, dependency resolution, payload generation, state tracking, validation, and reporting automatically.

Runtime never performs semantic analysis or asks AI to understand the API. Every execution decision has already been prepared during the parsing phase, allowing the runtime to remain deterministic, reproducible, and suitable for CI/CD environments.

## Phase 1 — Load Runtime Configuration

Blaster begins by loading the project configuration together with the synchronized endpoint configuration generated during the parsing phase.

Configuration values are resolved using a deterministic precedence order where built-in defaults are overridden by the project configuration, environment variables, and finally command-line flags.

Before execution begins, Blaster validates that every required resource is available, including configuration files, authentication settings, endpoint definitions, OpenAPI specification, and runtime options. Any critical configuration error immediately terminates execution before network activity begins.

Once validation succeeds, the runtime initializes its internal execution context, which contains immutable endpoint definitions together with the mutable runtime state used throughout execution.

## Phase 2 — Execution Planning

Before sending any HTTP request, Blaster constructs an execution plan.

The planner analyzes endpoint dependencies, authentication requirements, resource relationships, planner hints, and user-defined execution metadata to determine the safest execution order.

Whenever dependencies cannot be determined confidently, endpoints are treated as independent so execution remains deterministic instead of relying on uncertain assumptions.

The resulting execution plan is immutable. Runtime workers never decide execution order themselves and simply execute the tasks assigned by the planner.

## Phase 3 — Authentication

If reusable authentication tokens have already been provided by the project configuration, Blaster injects them directly into the runtime context.

Otherwise, Blaster performs the configured authentication workflow, extracts the required credentials from the authentication response, and stores them inside the runtime context for subsequent requests.

Authentication is performed only once before execution begins unless explicitly configured otherwise.

## Phase 4 — Resource Preparation

Some endpoints require existing resources before meaningful testing can begin.

When planner analysis determines that prerequisite resources are missing, Blaster performs an optional preparation phase that creates the minimum required dataset before concurrent execution starts.

Generated identifiers or reusable resource references are stored inside the runtime state so workers can immediately reuse them without repeatedly querying the backend.

Projects that already contain sufficient data automatically skip this phase.

## Phase 5 — Concurrent Execution

After preparation completes, Blaster executes the planner stages. The execution lifecycle described in Phase 5 through Phase 8 is repeated for every planner stage until the execution plan is fully completed.

Each stage contains one or more endpoint operations that can safely execute without violating planner constraints.

Within an execution stage, multiple workers execute requests concurrently to simulate realistic load while preserving deterministic execution boundaries between planner stages.

Workers never generate execution strategies themselves. They simply receive immutable execution tasks, construct request payloads, send HTTP requests, collect responses, and forward execution results to the validation pipeline.

Payload generation combines primitive type strategies, semantic rules generated during parsing, user-defined hybrid semantics, planner variables, and runtime state collected from previous stages.

## Phase 6 — Stateful Validation

Instead of validating only immediate HTTP responses, Blaster validates both the response itself and the observable backend state after every state-changing operation.

For mutation requests such as POST, PUT, PATCH, and DELETE, the runtime follows a consistent execution pattern.

The current resource state is retrieved before the mutation executes.

The mutation request is then performed.

Expected state changes are recorded inside the runtime state memory.

The latest backend state is retrieved again.

Finally, the validator compares the expected state with the actual backend state.

Validation focuses only on fields that were intentionally modified during execution. Fields that are unrelated, automatically generated, or known to change independently are ignored unless explicitly configured otherwise.

This approach significantly reduces false positives while verifying that backend state transitions actually occurred.

## Phase 7 — Runtime State Tracking

Every successful mutation updates the runtime state memory.

Rather than storing complete response bodies indefinitely, Blaster records only the information required for subsequent execution and validation, such as reusable identifiers, tracked field values, dependency references, and planner variables.

As execution progresses, newer successful mutations replace outdated expectations so validation always compares against the most recent known backend state.

This lightweight state model minimizes memory usage while enabling deterministic validation across long execution plans.

## Phase 8 — Validation Engine

Validation is performed asynchronously from request execution so that throughput remains unaffected.

The validation engine combines multiple deterministic verification layers.

The first layer validates transport behavior, including HTTP status codes, response schemas, protocol correctness, and response structure.

The second layer validates backend state transitions by comparing tracked runtime expectations against the latest observable resource state.

If optional AI assistance is enabled, AI is invoked only when deterministic validation cannot confidently explain suspicious behavior.

AI never replaces deterministic validation, modifies execution decisions, or determines whether a request passes or fails. It only provides additional semantic interpretation for ambiguous situations.

Instead of producing only binary results, every validation is classified into one of five confidence levels.

Wrong — deterministic evidence confirms incorrect behavior.
Possibly Wrong — behavior appears suspicious but cannot be proven conclusively.
Skipped — insufficient information exists for reliable evaluation.
Possibly Correct — behavior matches most expectations while minor uncertainty remains.
Correct — deterministic validation confirms expected behavior.

This confidence model communicates uncertainty explicitly rather than assuming every API can always be evaluated perfectly.

## Phase 9 — Reporting

Throughout execution, Blaster continuously aggregates execution metrics without interrupting concurrent workers.

After execution finishes, the reporter calculates request statistics, latency distributions, throughput, validation summaries, confidence classifications, and execution diagnostics.

Results are exported using formats suitable for both automated pipelines and human inspection, including CI-compatible reports together with an interactive HTML report for manual analysis.

## Phase 10 — Completion

After reporting completes, Blaster updates the runtime metadata required for future executions, releases all temporary resources, and exits using standard process status codes.

A successful execution returns an exit code indicating that all required validation criteria were satisfied.

If critical validation failures or configured failure thresholds are exceeded, Blaster returns a non-zero exit code so CI/CD pipelines can immediately detect deployment failures.

Runtime Design Philosophy

Blaster is not intended to replace carefully written integration tests, end-to-end tests, or business-specific validation suites.

Its objective is to provide the minimum safety net that every backend should have by automatically executing meaningful API validations from an OpenAPI specification with almost zero manual setup.

As developers gradually enrich endpoint metadata, semantic definitions, planner hints, and validation rules, the runtime becomes increasingly deterministic while remaining significantly simpler to maintain than hundreds of handwritten API test cases.
