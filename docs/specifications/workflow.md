# Workflow Specification

## Overview

Workflow defines deterministic execution order for API operations.

It never describes API structure, request schemas, response schemas, identities, payload generation, validation rules, runtime storage, or execution algorithms.

OpenAPI remains the Single Source of Truth (SSOT) for API definitions.

Endpoint remains the compiled runtime metadata generated by `blaster parse`.

Workflow defines only execution flow.

Planner combines OpenAPI, Endpoint, and Workflow to produce a compiled execution plan.

Runtime executes the compiled plan exactly as generated.

No runtime analysis, dependency discovery, semantic reasoning, AI inference, or workflow modification occurs during execution.

---

## Design Philosophy

Workflow intentionally answers only one question.

> Which operations should execute, and in what order?

Everything else belongs to another layer.

OpenAPI describes APIs.

Endpoint describes runtime identities and mappings.

Workflow describes execution order.

Planner analyzes.

Runtime executes.

Each component owns exactly one responsibility.

---

## Directory Layout

Workflow files are stored under the project workflow directory.

Example

```text
workflow/

    workflow.yaml

    default/

        users.workflow.yaml

        products.workflow.yaml

        categories.workflow.yaml

        orders.workflow.yaml

        cleanall.workflow.yaml
```

The root workflow imports child workflows.

Example

```yaml
version: "1.0"

imports:

  - default/users.workflow.yaml

  - default/products.workflow.yaml

  - default/categories.workflow.yaml

  - default/orders.workflow.yaml

  - default/cleanall.workflow.yaml
```

Planner expands imports before compilation.

Execution order follows the import order exactly.

---

## Flow

A workflow consists of ordered flow instructions.

Each line represents exactly one execution step.

Example

```yaml
flow:

  - get: /users, /products (ensure)

  - post: /users

  - get: /users (validate)

  - put: /users/{id}

  - get: /users (validate)
```

Planner never changes flow order.

Runtime executes each flow sequentially.

---

## Multiple Endpoints

One flow may execute multiple endpoints.

Example

```yaml
- get: /users, /products, /categories (ensure)
```

Planner expands the flow into independent execution units while preserving declaration order.

Workers may execute those units concurrently according to runtime configuration.

The logical workflow order never changes.

---

## Behaviors

Behaviors extend execution without modifying endpoint definitions.

Current built-in behaviors are

- ensure

- validate

Additional behaviors may be introduced in future versions without changing the execution model.

Behavior order is significant.

Planner preserves the declared order exactly.

---

## Ensure

Ensure guarantees enough runtime resources exist before later operations execute.

Ensure applies only to GET operations.

Planner first executes the GET request.

If enough resources already exist, execution continues normally.

If the available resource count is lower than the required runtime concurrency, Planner automatically traces the dependency graph backwards.

Planner discovers which producer operations are capable of creating the missing resources.

Those producer operations are executed automatically.

Planner retries the original GET until one of the following conditions becomes true.

- required resources become available

- retry limit is reached

- required producers cannot generate additional resources

Resources successfully created become normal runtime data.

Ensure never modifies the Workflow file.

It only affects Planner behavior.

---

## Validate

Validate verifies runtime correctness.

Workflow never specifies validation rules.

Planner generates validation rules automatically using OpenAPI together with Endpoint metadata.

Planner determines exactly which fields must be stored before execution begins.

Only fields required by later operations or later validation are preserved.

Unnecessary fields are discarded.

This minimizes runtime memory usage.

Example

If a later PUT operation only requires

```
id
```

Planner stores only

```
id
```

instead of the complete response object.

If a later validation requires

```
name

status
```

Planner additionally stores those fields.

Runtime never performs validation analysis.

Runtime executes the generated validation plan only.

---

## Resource Storage

Workflow never controls runtime storage.

Planner computes required runtime state during compilation.

Planner determines

- identities required by later requests

- fields required by validation

- fields required by later payload generation

- temporary runtime snapshots

Only required data is retained.

Everything else is discarded immediately.

This keeps runtime memory predictable regardless of response size.

---

## Identity Resolution

Workflow never defines identities.

Workflow never defines mappings.

Planner loads the compiled Endpoint produced by `blaster parse`.

Every Relative has already been resolved before workflow compilation begins.

Planner never performs endpoint analysis again.

Planner only consumes the compiled metadata.

---

## Default Workflows

Default workflows describe the normal lifecycle of a resource.

Example

```yaml
flow:

  - get: /users (ensure)

  - post: /users

  - get: /users (validate)

  - put: /users/{id}

  - get: /users (validate)

  - patch: /users/{id}

  - get: /users (validate)
```

Default workflows intentionally omit DELETE operations.

Resources remain available for workflows executed later.

---

## Cleanup Workflow

Cleanup is separated from normal resource workflows.

The cleanup workflow executes after all other workflows complete.

Example

```yaml
flow:

  - get: /users

  - delete: /users

  - get: /users (validate)
```

Planner automatically expands collection deletion into individual delete operations using stored identities.

Cleanup guarantees the testing environment is returned to a clean state.

---

## Workflow Generation

`blaster workflow` generates workflows automatically.

Generation is deterministic.

Planner analyzes

- OpenAPI

- Endpoint

- resource relationships

- identity producers

- relative consumers

Resource workflows are generated from simple resources toward more dependent resources.

Global resources appear before dependent resources.

Nested dependencies are generated after their producers.

This ordering minimizes dependency failures during execution.

---

## Planner

Planner performs all expensive analysis before runtime.

Planner loads

- OpenAPI

- Endpoint

- Workflow

Planner then

- resolves execution dependencies

- expands ensure operations

- generates payload plans

- generates validation plans

- determines runtime storage

- schedules worker execution

- builds the immutable execution plan

No additional planning occurs after compilation.

---

## Runtime

Runtime executes only the compiled execution plan.

Runtime never

- discovers identities

- resolves mappings

- generates payloads

- performs semantic reasoning

- analyzes workflows

- invokes AI

- modifies execution order

Runtime simply executes the deterministic plan produced by Planner.

---

## Future Extensions

Future versions may introduce

- custom workflow generators

- AI-assisted workflow generation

- visual workflow editors

- reusable workflow templates

- plugin-defined workflow generators

These features generate Workflow files only.

They never modify the execution model.

Planner and Runtime remain deterministic regardless of how Workflow files are created.
